# AWS KMS, DEK, and HMAC — How They Fit Together

## The key hierarchy

There are two levels. AWS KMS only appears at the top.

```
AWS KMS Master Key          ← one symmetric key per environment, lives entirely in AWS KMS
        │
        │  KMS.GenerateDataKey / KMS.Decrypt  (called once per startup, not per transaction)
        ▼
   DEK — Data Encryption Key          ← 32 bytes, generated by KMS (GenerateDataKey)
        │  stored encrypted as BYTEA in key_versions.encrypted_dek_blob
        │  one DEK per rotation period (shared by all PANs in that period)
        │
        ├───────────────────────────────────────────────┐
        │  AES-256-GCM  (in-process, no KMS call)       │  KMS.Encrypt directly
        ▼                                               ▼
   PAN ciphertext                               HMAC Secret
   token_vault.encrypted_pan + iv + auth_tag    32 bytes, generated locally
                                                stored encrypted in
                                                key_versions.encrypted_secret (BYTEA)
```

### What AWS provides vs what the app provides

| Material | Who generates it | Where it lives at rest |
|----------|-----------------|----------------------|
| KMS Master Key | AWS KMS | Inside AWS KMS — never leaves |
| DEK (32 bytes) | AWS KMS — `GenerateDataKey` | `key_versions.encrypted_dek_blob` (KMS-encrypted, BYTEA) |
| HMAC secret (32 bytes) | App — `SecureRandom` | `key_versions.encrypted_secret` (KMS-encrypted, BYTEA) |

**AWS generates the DEK.** This is the key difference from a 3-layer design: the application never calls `SecureRandom` to produce a DEK — KMS does, returning both the plaintext (for immediate use) and the encrypted blob (for storage). The trust chain is: KMS Master Key → DEK/HMAC (both wrapped by the same CMK, with distinct encryption contexts to prevent cross-use).

## How it starts up

`KeyRingInitialiser` runs in two phases before the app accepts traffic.

**Phase 1 — load DEK ring:**

```
SELECT * FROM key_versions WHERE key_type = 'DEK' AND status IN ('ACTIVE', 'ROTATING')

For each row:
  dek_bytes  = KmsClient.decrypt(encrypted_dek_blob, context = {purpose: "data-key"})   ← KMS call
  dekRing.load(version_id, dek_bytes, rotate_by)

dekRing.promoteActive(active_version_id)
zero(dek_bytes)
```

**Phase 2 — load HMAC ring:**

```
SELECT * FROM key_versions WHERE key_type = 'HMAC' AND status IN ('ACTIVE', 'ROTATING')

For each row:
  hmac_secret  = KmsClient.decrypt(encrypted_secret, context = {purpose: "hmac-key"})   ← KMS call
  hmacRing.load(version_id, hmac_secret)

hmacRing.promoteActive(active_version_id)
zero(hmac_secret)
```

After startup, KMS is not called again until the next restart or until a new DEK version row is created. All tokenisation, detokenisation, and rotation batches run entirely in JVM memory.

## How a token is created

```
pan_bytes        = PAN.getBytes(UTF-8)
dek              = dekRing.getActive().copyDek()     ← from in-memory ring, no KMS
iv               = SecureRandom.nextBytes(12)         ← fresh per encryption — CRITICAL
encrypted_pan    = AES-GCM.encrypt(pan_bytes, dek, iv)
auth_tag         = GCM authentication tag (16 bytes)
pan_hash         = HMAC-SHA256(pan, active_hmac_secret)   ← hmac secret from in-memory ring
zero(dek, pan_bytes)

INSERT token_vault (token_id, token, encrypted_pan, iv, auth_tag,
                    key_version_id, pan_hash, hmac_key_version_id, ...)
```

No KMS call. No per-record DEK generated or stored.

**Why the fresh IV is critical:** The same DEK encrypts all PANs within a rotation period. AES-GCM is a stream cipher — `ciphertext = plaintext XOR keystream(DEK, IV)`. Reusing an IV means reusing the keystream: an attacker could XOR two ciphertexts to recover `PAN1 XOR PAN2`. A fresh 12-byte random IV per encryption guarantees unique `(DEK, IV)` pairs across the lifetime of the key.

## DEK rotation — step by step

**Trigger:** `POST /api/v1/admin/keys/rotate` or compliance cron.

**Step 1 — Initiate:**
```
App:  dataKey    = kmsProvider.generateDataKey()       ← one KMS call (GenerateDataKey)
                   returns {plaintextDek, encryptedDekBlob}

DB:   UPDATE key_versions SET status = 'ROTATING' WHERE id = v1
DB:   INSERT key_versions (encrypted_dek_blob = dataKey.encryptedDekBlob,
                           key_type = 'DEK', status = 'ACTIVE') → v2

Ring: dekRing.load(v2, plaintextDek, rotateBy)
      dekRing.promoteActive(v2)
      zero(plaintextDek)

Audit: KEY_ROTATION_STARTED
```

From this moment new tokenisations write `key_version_id = v2`. Old tokens with `v1` remain
detokenisable — v1 is still in the ring (ROTATING, not removed).

**Step 2 — Batch re-encryption (cron: every 15 min, batch size: 500):**
```
SELECT * FROM token_vault WHERE key_version_id = v1 AND is_active = TRUE LIMIT 500

For each token:
  old_dek       = dekRing.getByVersion(v1).copyDek()
  new_dek       = dekRing.getByVersion(v2).copyDek()
  pan_bytes     = AesGcmCipher.decrypt(encrypted_pan, iv, auth_tag, old_dek)   ← no KMS
  new_result    = AesGcmCipher.encrypt(pan_bytes, new_dek)                     ← fresh IV
  zero(old_dek, new_dek, pan_bytes)

  UPDATE token_vault SET
      encrypted_pan  = new_result.ciphertext(),
      iv             = new_result.iv(),
      auth_tag       = new_result.authTag(),
      key_version_id = v2
  WHERE token_id = X
  Audit: TOKEN_REENCRYPTED
```

Each token gets a fresh IV on re-encryption. If the app restarts mid-batch: both v1 (ROTATING)
and v2 (ACTIVE) are reloaded into the ring on startup. The job resumes from whatever rows still
have `key_version_id = v1`.

**Step 3 — Completion (auto-detected):**
```
countActiveByKeyVersionId(v1) == 0

DB:   UPDATE key_versions SET status = 'RETIRED' WHERE id = v1
Ring: dekRing.retire(v1)
Audit: KEY_ROTATION_COMPLETED
```

## HMAC rotation — step by step

Like DEK rotation, HMAC rotation **generates genuinely new cryptographic material**.

**Why HMAC needs rotation:** The HMAC secret is used to compute `pan_hash` for deduplication.
Rotating it requires re-hashing every PAN in the vault — the one batch that decrypts PAN
plaintext outside of a live detokenisation request.

**Trigger:** `POST /api/v1/admin/hmac-keys/rotate`

**Step 1 — Initiate:**
```
App:  new_hmac_bytes = SecureRandom.nextBytes(32)           ← genuinely new material
KMS:  enc_secret     = KmsClient.encrypt(new_hmac_bytes, context = {purpose: "hmac-key"})
                       ← one KMS call

DB:   UPDATE key_versions SET status = 'ROTATING' WHERE id = h1
DB:   INSERT key_versions (key_type = 'HMAC', encrypted_secret = enc_secret,
                           ...) → h2, status = 'ACTIVE'
Ring: hmacRing.load(h2, new_hmac_bytes); hmacRing.promoteActive(h2)
      zero(new_hmac_bytes)

Audit: HMAC_ROTATION_STARTED
```

From this moment new tokenisations hash with h2. Old vault rows still carry the h1 hash.

**Dual-lookup deduplication during the rotation window:**

Without this, the same PAN tokenised before and after initiation would produce two different
`pan_hash` values and get two different tokens — breaking deduplication.

```
// TokenisationService
new_hash = HMAC(pan, active_hmac=h2)
existing = vault.findByPanHash(new_hash)

if not found:
    rotating_id = hmacRing.findRotatingVersionId()   // returns h1
    if present:
        old_hash = HMAC(pan, h1_secret)
        existing = vault.findByPanHash(old_hash)     // finds the old record
        // returns same token — no duplicate issued
```

**Step 2 — Batch re-hash (cron: daily 02:00 UTC, batch size: 100):**
```
SELECT * FROM token_vault WHERE hmac_key_version_id = h1 AND is_active = TRUE LIMIT 100

For each token:
  dek_bytes    = dekRing.getByVersion(token.key_version_id).copyDek()
  pan_bytes    = AesGcmCipher.decrypt(encrypted_pan, iv, auth_tag, dek_bytes)
  new_hash     = HMAC-SHA256(pan_bytes, hmacRing.getActiveSecret())
  zero(dek_bytes, pan_bytes)

  UPDATE token_vault SET pan_hash = new_hash, hmac_key_version_id = h2 WHERE token_id = X
  Audit: PAN_HASH_RECOMPUTED
```

This decrypts PAN plaintext in memory — no KMS call, but the most sensitive batch in the
system. Parallelism is limited to 4 threads (vs 8 for DEK rotation) to reduce exposure window.

**Step 3 — Completion (auto-detected):**
```
countActiveByHmacVersionId(h1) == 0

DB:     UPDATE key_versions SET status = 'RETIRED' WHERE id = h1
Ring:   hmacRing.retire(h1)
Audit:  HMAC_ROTATION_COMPLETED
```

## Resumability

Both jobs are fully resumable across restarts.

`KeyRingInitialiser` always loads **ACTIVE and ROTATING** DEK versions at startup. If the app
restarts mid-rotation, both the old (ROTATING) and new (ACTIVE) versions reload into the ring.
The batch job resumes from wherever `WHERE key_version_id = v1` still has records — it never
needs to know how far it got before the restart.

## KMS call budget

| Operation | KMS calls |
|-----------|-----------|
| App startup (normal) | 1 — decrypt the ACTIVE DEK blob |
| App startup (mid-rotation) | 2 — decrypt ACTIVE + ROTATING DEK blobs |
| Per-token tokenise | 0 |
| Per-token detokenise | 0 |
| DEK rotation initiate | 1 — `GenerateDataKey` (returns plaintext + encrypted blob in one call) |
| DEK rotation batch (per record) | 0 — in-memory AES-GCM only |
| HMAC rotation initiate | 1 — `KMS.Encrypt(new_hmac_bytes)` |
| HMAC rotation batch (per record) | 0 — in-memory AES-GCM + HMAC only |

KMS is a **startup-and-rotation-initiation-only dependency**. If KMS becomes unavailable
after the app has started, all tokenise/detokenise operations continue unaffected. KMS is only
required again on the next restart or when a new key version row is being created.

---

## Operational sequencing for concurrent rotation

**Never run DEK and HMAC rotation simultaneously.** If a HMAC batch record's DEK becomes
`COMPROMISED` during a concurrent emergency DEK rotation, the HMAC batch emits
`RE_HASH_SKIPPED_COMPROMISED_KEY` and skips that record. Those records are picked up again
after the DEK batch completes and re-encrypts their PANs under the new DEK.

Recommended sequence for a full scheduled rotation:
1. Trigger HMAC rotation → wait for batch to complete (all `hmac_key_version_id` updated)
2. Trigger DEK rotation → runs every 15 min until all `key_version_id` updated
3. Confirm both old versions are `RETIRED` in audit log / health endpoint
